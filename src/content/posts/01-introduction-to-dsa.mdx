## 1. Introduction — 為什麼需要資料結構與演算法？

假設我們正在開發一個線上圖書館管理系統，裡面儲存了數百萬筆書籍資料。

系統可能需要完成以下操作：

- 根據 ISBN 查詢特定書籍
- 新增或刪除書籍紀錄
- 按照借閱時間管理預約佇列
- 找出目前借閱次數最多的書籍
- 按照書籍分類建立階層式目錄

從使用者的角度來看，這些功能可能都相對直觀。但從程式設計的角度來看，我們則需要回答兩個重要的問題：

1. **資料應該如何被儲存？**
2. **應該透過什麼方式來操作這些資料？**

第一個問題對應 Data Structures，第二個問題對應 Algorithms。

兩者密不可分。即使兩個程式能夠得到完全相同的結果，它們所需要的運算時間與記憶體空間，也可能有極大的差異。

例如，我們要從一百萬筆資料中尋找某個指定的 ISBN。

如果採用最直觀的方式，從第一筆資料開始逐一比較，在最差情況下可能需要檢查一百萬筆資料。

但如果我們事先建立合適的索引結構，就可能大幅減少查詢成本。

因此，資料結構與演算法的核心目的之一，就是研究 **「如何有效率地利用資料，以及如何有效率地解決問題。」**

## 2. What Is a Data Structure?

### 2.1 資料結構的定義

**Data Structure（資料結構）** 是一種組織、儲存與管理資料的方式，讓程式能依照特定需求去有效地存取與修改資料。

一個資料結構通常涉及三個面向：

1. **Data Organization**：資料之間如何組織與關聯
2. **Supported Operations**：可以對資料執行哪些操作
3. **Implementation & Performance**：具體如何執行，以及不同的操作需要多少成本

舉例，一個 Stack（堆疊）通常會有：

| Operation   | Description   |
| ----------- | ------------- |
| `push(x)`   | 將元素 x 加入頂端  |
| `pop()`     | 移除並回傳頂端元素（Top Element）    |
| `peek()`    | 僅讀取頂端元素  |
| `isEmpty()` | 判斷 Stack 是否為空 |

`push(x)` 這邊有點類似於 Python 裡面 list 的 `append(x)` 操作。
- `push()` 是概念層
- `append()` 則是實作層。

> Stack 的核心規則稱為 **Last-In, First-Out（LIFO）**，也就是「最後放入的元素會最優先被取出！」。

### 2.2 為什麼不用 Python List 來介紹就好？

雖然 Python 已經提供 `list`、`dict`、`set` 等內建資料型態，不需要自行實作資料結構。

但不同的資料結構對成本效率還是會有所不同。

例如：

```python
books = ["Book A", "Book B", "Book C"]

# Method 1. 取得最後一本書
last_book = books[-1]

# Method 2. 在最前面插入一本書
books.insert(0, "Book D")
```

**這兩個 Methods 雖然都只需要一行程式碼，但它們的執行成本卻不一定相同！**

在 Python 的 `list` 中：

- `books[-1]`：一般情況下是 O(1)。
- `books.insert(0, value)`：需要移動既有元素，時間複雜度為 O(n)。

其中 n 代表 List 目前包含的元素數量。

這也說明了：

> 程式碼的行數與演算法的時間複雜度並沒有直接關係。一行程式可能執行大量工作；相反地，多行固定成本的程式也可能具有 O(1) 時間複雜度。簡單來說，就是即便簡單的幾行程式碼，背後的執行成本有可能是極高的！

## 3. What Is an Algorithm?

### 3.1 演算法的定義

**Algorithm（演算法）** 是一組明確、可執行的步驟，用來處理輸入的資料並解決特定問題。

一般而言，我們會希望演算法具備以下幾種特性：

- **Input**：接受零個或多個輸入。
- **Output**：產生符合問題要求的結果。
- **Definiteness**：每個步驟都有明確的意義。
- **Effectiveness**：每個基本步驟都可以實際執行。
- **Finiteness**：對於規定的有效輸入，演算法應在有限步驟內完成。

這裡需要注意：並非所有研究中的計算程序都保證終止，但在一般入門演算法問題中，我們通常要求演算法能夠正確終止。

### 3.2 Example: Linear Search

先假設我們有以下資料：

```python
numbers = [12, 45, 7, 23, 91]
```

現在希望找到數字 `23` 的位置。

最直觀的方式，就是從第一個元素開始逐一比對。

```python
def linear_search(arr, target):
    # 逐一檢查陣列中的元素
    for i in range(len(arr)):

        # 如果目前元素等於目標值
        if arr[i] == target:
            return i

    # 如果全部檢查完仍然找不到
    return -1
```

呼叫方式：

```python
numbers = [12, 45, 7, 23, 91]

result = linear_search(numbers, 23)

print(result)  # Output: 3
```

### 3.3 Step-by-Step Execution

假設目標值為 `23`。

| Step | Index | Current Value | Match? |
| ---- | :----: | :------------: | :-----: |
| 1    |     0 |            12 | No     |
| 2    |     1 |            45 | No     |
| 3    |     2 |             7 | No     |
| 4    |     3 |            23 | Yes    |

找到目標值後，演算法立即回傳索引 `3`！

但如果目標值不存在，就必須從頭到尾 run through 檢查全部元素：）

假設陣列長度為 n，最差情況下需要 n 次元素比較，因此：

$$
T_{\text{worst}}(n) = \Theta(n)
$$

這種搜尋方法稱為 Linear Search（線性搜尋）。

### 3.4 Algorithm Correctness

演算法的第一個要求是 **Correctness（正確性）**。

我們可以將 Linear Search 的正確性分成兩部分：

**Part A：如果演算法回傳索引 i，該結果一定正確。**

因為演算法只有在以下條件成立時才會回傳 i：

$$
A[i] = target
$$

因此，只要回傳某個索引，該索引必然對應到目標值。

**Part B：如果演算法回傳 -1，代表目標值不存在。**

因為演算法會檢查所有合法索引：

$$
i \in \{0,1,\ldots,n-1\}
$$

若所有元素都不等於 target，迴圈才會結束並回傳 -1。

此外，迴圈最多執行 n 次，因此一定會終止。

綜合以上，可以確認 Linear Search 對有限長度的陣列具有正確性與終止性。

這個範例也建立了演算法設計的重要觀念：

> 一個好的演算法不只需要能得到正確答案，還應該能夠說明它為什麼對所有符合規則的 Input 都正確。

## 4. Abstract Data Types (ADT) — 抽象資料型態

### 4.1 ADT 是什麼？

Abstract Data Type（ADT）是一種描述資料型態行為的抽象模型。

它定義：

- 可以儲存什麼類型的資料。
- 支援哪些操作。
- 每個操作應該具有什麼行為。

但 ADT 不要求使用特定的底層資料結構。

例如 Stack ADT 規定：

- `push(x)` 將元素加入頂端（Top）。
- `pop()` 移除並回傳頂端元素。
- `peek()` 僅讀取並回傳頂端元素。
- 元素的移除順序必須符合 LIFO（Last In, First Out）。

此外，Stack 還可以透過不同方式實作：

- Array-based Stack
- Linked-list-based Stack

只要符合 Stack ADT 的規定，就可以視為有效的 Stack 實作。

### 4.2 ADT vs Data Structure vs Algorithm

以上這三個概念經常被混淆，所以這邊特別拿出來講一下。

| Concept        | 核心問題                           | Example              |
| -------------- | ------------------------------ | -------------------- |
| ADT            | What operations are supported? | Stack                |
| Data Structure | How is the data organized?     | Linked List          |
| Algorithm      | How is an operation performed? | `push()` or `pop()` |

以 Stack 為例：

**ADT** 規定我們必須遵守 LIFO；**Data Structure** 則決定要使用 Array 還是 Linked List 來儲存元素；而 **Algorithm** 決定 `push()` 和 `pop()` 具體需要執行哪些步驟。

### 4.3 Stack ADT 的數學描述

我們可以將 Stack 表示為一個有限序列：

$$
S = (x_1,x_2,\ldots,x_n)
$$

其中 $x_n$ 為頂端元素。

執行：

$$
push(S,x)
$$

得到：

$$
S' = (x_1,x_2,\ldots,x_n,x)
$$

執行：

$$
pop(S')
$$

則會移除最後一個元素 x，並恢復原本的 Stack。

因此：

$$
pop(push(S,x)) = x
$$

這裡的等式表示 `pop` 回傳的元素值為 x，而不是表示兩個操作後的 Stack 物件本身等於 x。

這個性質反映了 Stack 的 LIFO 行為。

### 4.4 Python Implementation: Stack Using List

首先，我們使用 Python List 實作簡單的 Stack。

```python
class Stack:
    def __init__(self):
        # 儲存 Stack 的所有元素
        self.items = []

    def push(self, value):
        # 將新元素加入 List 尾端
        self.items.append(value)

    def pop(self):
        # 移除並回傳最後一個元素
        if self.is_empty():
            raise IndexError("Stack is empty")

        return self.items.pop()

    def peek(self):
        # 讀取頂端元素，不修改 Stack
        if self.is_empty():
            raise IndexError("Stack is empty")

        return self.items[-1]

    def is_empty(self):
        # 沒有任何元素時回傳 True
        return len(self.items) == 0
```

實作範例如下：

```python
stack = Stack()

stack.push(10)
stack.push(20)
stack.push(30)

print(stack.peek())  # 30
print(stack.pop())   # 30
print(stack.pop())   # 20
print(stack.peek())  # 10
```

在這個實作中：

| Operation | Time Complexity |
| --------- | --------------- |
| push      | Amortized O(1)  |
| pop       | O(1)            |
| peek      | O(1)            |
| is_empty  | O(1)            |

Python List 是動態陣列（Dynamic Array）。當底層儲存空間不足時，可能需要重新配置空間並複製元素，因此 `append()` 的單次最差時間不一定是 O(1)，而是 Amortized O(1)。

不過，透過 Amortized Analysis（攤銷分析，或者我們說均攤分析，後面會再特別說明），可以證明一連串 Append 操作的平均攤銷成本是 O(1)。

## 5. Classification of Data Structures — 資料結構的分類

資料結構可以依照資料之間的邏輯關係分成不同類型。

### 5.1 Linear Data Structures

Linear Data Structures（線性資料結構）將元素組織成具有線性順序的結構。

常見類型包括：

- Array
- Linked List
- Stack
- Queue

它們具有不同的操作規則與效率特性。

例如，Array 支援直接索引存取；Linked List 則透過節點參照建立元素之間的連結。

### 5.2 Non-Linear Data Structures

Non-Linear Data Structures（非線性資料結構）不要求所有元素都排列成單一線性序列。

常見類型包括：

- Trees
- Heaps
- Graphs

例如，Binary Tree 中每個節點最多有兩個子節點。

Tree 的階層式關係適合用來表示：

- 檔案系統目錄
- 組織架構
- 搜尋索引
- 運算式語法樹

而 Graph 可以表示更一般的關係，例如電腦網路、交通路線或社群網絡。

### 5.3 Hash Tables

Hash Table（雜湊表）利用 Hash Function 將 Key 映射到儲存位置。

它不適合單純歸類為一般線性或樹狀結構，而是另一種以快速查詢為核心目標的資料組織方式。

在適當條件下，Hash Table 可以達到預期 O(1) 的查詢效率。

不過，碰撞（Collision）、負載因子（Load Factor）與雜湊函數品質，都會影響實際效能。

### 5.4 Overview of Common Data Structures

| Data Structure | 主要特性             | 常見用途             |
| -------------- | ---------------- | ---------------- |
| Array          | 連續索引存取           | 固定順序資料           |
| Linked List    | 節點透過參照連結         | 動態插入與刪除          |
| Stack          | LIFO             | Undo、Call Stack  |
| Queue          | FIFO             | 任務排程、請求處理        |
| Tree           | 階層式關係            | 搜尋、目錄管理          |
| Hash Table     | Key-based Lookup | Dictionary、Cache |
| Heap           | 維護優先順序           | Priority Queue   |
| Disjoint Set   | 集合合併與代表元查詢       | 連通性問題            |

**注意：** 資料結構並不是依照名稱就能保證某個時間複雜度。實際效率仍取決於底層實作、操作方式及分析條件。

## 6. Memory Representation — 資料如何儲存在記憶體中？

理解資料結構之前，我們需要建立一些記憶體模型的基本概念。

### 6.1 Contiguous Memory

在典型的低階 Array 實作中，相同型態的元素會儲存在連續的記憶體位置。

假設每個元素佔用 w bytes，第一個元素的位址為 B。

那麼第 i 個元素的位址可以表示為：

$$
Address(A[i]) = B + i \times w
$$

其中 i 從 0 開始。

例如：

$$
B = 1000,\quad w = 4
$$

則：

$$
Address(A[3]) = 1000 + 3(4) = 1012
$$

這代表我們可以直接計算元素的位置，不需要從第一個元素逐一走訪。

在標準的 RAM（Random Access Machine）成本模型下，這類索引存取通常視為 O(1)。

不過，這個模型是抽象化的。實際硬體還涉及 Cache、Memory Hierarchy、Virtual Memory 等因素。

另外，Python List 儲存的是物件參照，並不是把所有 Python 物件內容直接連續放在同一塊記憶體中。

### 6.2 Linked Memory Representation

Linked List 採用不同的設計。

每個節點包含：

1. Data：儲存資料。
2. Reference / Pointer：指向其他節點。

例如：

```python
class Node:
    def __init__(self, value):
        # 節點儲存的資料
        self.value = value

        # 指向下一個節點
        self.next = None
```

建立三個節點：

```python
node1 = Node(10)
node2 = Node(20)
node3 = Node(30)

# 建立節點之間的連結
node1.next = node2
node2.next = node3
```

邏輯結構為：

```text
Head
 |
 v
[10] -> [20] -> [30] -> None
```

與 Array 不同，Linked List 的節點不需要在記憶體中連續排列。

但如果我們要找到第三個節點，通常必須從 Head 開始沿著連結走訪。

因此，Singly Linked List 中透過位置尋找第 i 個元素，一般需要 O(i) 時間。

這也顯示不同的資料組織方式會直接影響操作效率。

## 7. Time and Space Complexity — 如何衡量效率？

### 7.1 為什麼不能只測量執行秒數？

假設兩個演算法執行相同任務：

- Algorithm A：0.01 秒。
- Algorithm B：0.03 秒。

是否代表 A 一定比較好？

不一定。

因為實際執行時間可能受到以下因素影響：

- CPU 效能
- 記憶體速度
- 程式語言與執行環境
- 編譯器或直譯器
- 輸入資料規模與分布
- 作業系統負載

因此，我們需要一種更抽象的分析方式。

### 7.2 Input Size

令 n 表示 Input Size（輸入規模）。

例如：

- Array：n 可以是元素數量。
- Linked List：n 可以是節點數量。
- Graph：通常需要同時考慮頂點數 V 與邊數 E。
- Integer Algorithm：輸入大小可能是整數的位元長度，而不是整數本身的數值。

接著，我們定義：

$$
T(n)
$$

表示演算法在輸入規模 n 下的執行成本。

這裡的成本通常以基本操作次數衡量，而非直接使用秒數。

### 7.3 Constant Time — O(1)

考慮：

```python
def get_first(arr):
    return arr[0]
```

假設輸入是非空的 Python List，這個操作不需要遍歷整個陣列。

即使陣列有一百萬個元素，也只需要一次索引存取。

因此：

$$
T(n) = \Theta(1)
$$

也可以寫成：

$$
T(n) = O(1)
$$

這裡的 1 並不是代表執行一秒，也不是只能執行一行程式。

它代表成本具有與 n 無關的常數上界。

### 7.4 Linear Time — O(n)

考慮：

```python
def find_max(arr):
    # 假設 arr 至少有一個元素
    maximum = arr[0]

    # 從第二個元素開始比較
    for value in arr[1:]:
        if value > maximum:
            maximum = value

    return maximum
```

假設陣列有 n 個元素。

這個演算法需要檢查每個元素是否大於目前最大值。

因此基本比較次數隨 n 線性增加：

$$
T(n) = an + b
$$

其中 a、b 是常數。

所以：

$$
T(n) = \Theta(n)
$$

需要注意的是，`arr[1:]` 在 Python 中會建立新的 List，額外使用 O(n) 空間。

如果希望避免複製，可以改成：

```python
def find_max(arr):
    if not arr:
        raise ValueError("Array must not be empty")

    maximum = arr[0]

    for i in range(1, len(arr)):
        if arr[i] > maximum:
            maximum = arr[i]

    return maximum
```

這個版本的時間複雜度仍然是：

$$
T(n)=\Theta(n)
$$

但額外空間複雜度為：

$$
S(n)=\Theta(1)
$$

這個例子說明了時間與空間成本需要分開分析。

### 7.5 Quadratic Time — O(n²)

考慮雙層迴圈：

```python
def print_pairs(arr):
    n = len(arr)

    for i in range(n):
        for j in range(n):
            print(arr[i], arr[j])
```

外層迴圈執行 n 次。

每一次外層迴圈，內層迴圈也執行 n 次。

因此總迭代次數為：

$$
n \times n = n^2
$$

所以：

$$
T(n)=\Theta(n^2)
$$

這裡假設每次輸出操作的成本視為常數；實際 I/O 成本可能更複雜。

### 7.6 Common Complexity Classes

| Complexity | Name         | 典型情境           |
| ---------- | ------------ | -------------- |
| O(1)       | Constant     | Array Indexing |
| O(log n)   | Logarithmic  | Binary Search  |
| O(n)       | Linear       | Linear Search  |
| O(n log n) | Linearithmic | Merge Sort     |
| O(n²)      | Quadratic    | Nested Loops   |
| O(2ⁿ)      | Exponential  | 某些子集合枚舉        |
| O(n!)      | Factorial    | 暴力枚舉所有排列       |

對於足夠大的 n，常見的成長關係為：

$$
1 < \log n < n < n\log n < n^2 < 2^n < n!
$$

這裡比較的是成長階數；不代表對所有小 n，這些函數值都嚴格依照相同順序排列。

## 8. Tradeoffs — 為什麼沒有最好的資料結構？

資料結構的設計通常涉及取捨。

例如：

- Array 提供快速索引存取，但在開頭插入元素可能需要移動大量資料。
- Linked List 可以在已知節點位置的情況下快速修改連結，但不支援一般意義上的 O(1) 隨機索引存取。
- Hash Table 通常提供快速的 Key Lookup，但不一定維持 Key 的排序關係。
- Balanced Search Tree 能夠維護排序，並提供 O(log n) 的搜尋、插入與刪除操作。

因此，選擇資料結構之前，應該先分析：

1. 哪些操作最頻繁？
2. 資料是否需要排序？
3. 資料規模可能成長到多大？
4. 是否有記憶體限制？
5. 是否需要保證 Worst-case Performance？
6. 是否需要處理大量動態更新？

### Example: Choosing a Data Structure

假設要設計一個線上商店的訂單處理系統。

**需求 A：依照訂單到達順序處理**

適合使用 Queue，因為它遵守 FIFO。

**需求 B：快速查詢訂單編號**

可以考慮 Hash Table，利用 Order ID 作為 Key。

**需求 C：優先處理緊急訂單**

可以考慮 Priority Queue，並使用 Heap 實作。

**需求 D：按照價格範圍查詢商品**

可以考慮維護排序的 Tree-based Index。

由此可見，真實系統通常不會只使用單一資料結構，而是根據不同操作需求組合多種資料結構。

## 9. Common Misconceptions — 常見觀念錯誤

### Misconception 1：程式碼越短，執行效率越高

程式碼長度不等於執行成本。

```python
target in values
```

雖然只有一行，但如果 `values` 是一般 Python List，最差情況下仍可能需要 O(n) 次比較。

### Misconception 2：O(1) 代表執行時間永遠相同

O(1) 代表漸近成本具有常數上界，不代表真實執行時間完全固定。

硬體快取、記憶體配置與執行環境仍可能造成差異。

### Misconception 3：Big-O 只用來分析 Worst Case

不完全正確！Big-O 是漸近上界記號，可以描述 Worst-case、Average-case、Expected 或 Amortized 成本函數。

分析時必須明確指出所討論的成本模型與情境。

### Misconception 4：所有資料結構都有固定的最佳實作方式

相同 ADT 可以透過不同資料結構實作。

例如 Queue 可以透過：

- Linked List
- Circular Array
- Two Stacks

來實作。

不同實作方式可能具有不同的操作成本與記憶體需求！

### Misconception 5：時間複雜度比較低的演算法一定比較快

不一定。當 n 很小時，常數因素可能主導實際執行時間。所以還是需要根據當下情境去判斷！

例如：

$$
T_A(n)=1000n
$$

$$
T_B(n)=n^2
$$

雖然 A 是線性成長、B 是平方成長，但在某些較小的 n 下，B 的實際操作數可能更少。

Big-O 主要描述輸入規模增加時的漸近行為，不能完全取代實際效能測量。

## 11. Chapter Summary

在本章中，我們建立了資料結構與演算法的基本概念。

**Data Structure** 關心資料如何被組織與儲存。

**Algorithm** 關心如何透過明確步驟解決問題。

**Abstract Data Type（ADT）** 定義資料型態的行為與操作規格，但不指定具體實作。

而 **Complexity Analysis** 則提供一套分析方法，讓我們能夠比較不同演算法與資料結構的效率。

本章最重要的觀念是：

> There is no universally optimal data structure. The right choice depends on the operations, constraints, and performance requirements of the problem.

沒有任何資料結構適用於所有情境。真正重要的是理解每種資料結構的設計目的、操作成本與限制，並根據問題需求選擇適當的解決方案。
